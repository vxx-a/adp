# Architecture

Architecture is the first development step. Complete these notes before building its skill or agent. Program design follows.

## Scope

- System purpose, users, and external systems.
- Module responsibilities, data ownership and storage, dependencies, and direct calls or messaging.
- Shared decisions: tech stack, auth, config and secrets, logging and monitoring, deployment and environments.

Program design defines gRPC services, protobuf messages, internal layers, packages, and components, and how each module implements the shared decisions. Implementation defines classes and functions.

Follow `template/AGENTS.md`: Dockerize each module, use gRPC between modules, and review modules approaching 10k lines for a possible split.

## Design principles

A module is a separately deployed service.

- **Use as few modules as the needs allow.** Split only for a named need for independent scaling, deployment, security, or failure isolation. Data ownership alone doesn't require a separate service.
- **Draw boundaries around business capabilities**, such as orders or billing, rather than technical layers such as API or database. Most changes within a business capability should stay within its module. Frequent coordinated changes across modules are a reason to reconsider their boundaries.
- **Review modules approaching 10k lines.** Split only where responsibilities form a clear boundary; size alone doesn't require a split.
- **Each module owns its data.** Modules never access another module's tables; they use its contract. Capabilities within a module can also have distinct data owners.
- **Dependencies go one way.** No cycles between modules.
- **Modules call each other directly by default.** Use a message queue only for a named reason: work can happen later, several modules react to it, or the caller must keep working when the receiver is down. Every remote call needs a deadline and defined failure behavior. Retry side effects only when duplicate execution is safe. Queues need explicit retry and duplicate-handling behavior too.
- **Keep operations that must succeed or fail together within one module where practical.** When an operation spans modules, define what happens if only part succeeds.
- **Prefer stateless application processes.** Keep durable state in datastores. Avoid correctness depending on a particular replica's memory, and handle concurrent work safely when adding replicas.
- **Design for the load in the project file, with headroom.** Specify peak traffic, data volume, and latency targets. Write down what would change beyond that load, but don't build it.
- **Choose boring, well-known tech.** Bring in something new only when a need in the project file requires it.
